# I trained a 34M-parameter log model from scratch. Here is what worked, what didn't, and what I got wrong.

*Draft. All numbers are from this repo (`results/`, `docs/`); every claim below has a script behind it.*

On-call engineers and AI SRE agents drown in logs. The obvious fix — pipe everything into a frontier
LLM — is slow, expensive, and often blocked by privacy rules. The classic alternative (template
parsers + an LSTM) can tell you *that* something is wrong, but not *which lines* explain it.

LogLens is my attempt at the missing piece: a small model that reads raw logs on a CPU and hands an
agent the ~15 lines that matter out of thousands. This post is mostly about the parts that surprised
me, because the headline number is the least interesting thing in the repo.

## What I built

- **A log-aware tokenizer.** Ordered regex masking (`<IP>:<PORT>`, `<UUID>`, `<PATH>`, bucketed
  `<DURATION:10s+>`, small status codes kept literal) followed by byte-level BPE. 80+ unit tests, plus
  a parity test between a guarded fast path and the reference implementation.
- **A two-level model.** A 33.6M-parameter line encoder (8 layers, d=512) turns each *distinct* masked
  line into a 256-d embedding; a 4-layer window model reads 256 lines of embeddings plus a time-gap,
  service and level embedding, and has an anomaly head, a per-line suspicion head, and a masked-line
  template head for unsupervised scoring.
- **A fault-injection lab** with 10 fault types and causal-line labels — as a *simulator*, because my
  laptop has no Docker. That single fact shapes every result below.
- **An int8 ONNX runtime** with an embedding cache, a CLI, an HTTP API and an agent tool.

## The headline number, and why to distrust it

On 36 held-out synthetic lab incidents, LogLens puts a causal line in its top 5 for **94%** of
incidents (Recall@1 61%, MRR 0.76), versus 81% for an LSTM's surprise score and 17% for random. An
agent handed the top 15 lines reads **~140x fewer tokens** than one reading the raw incident window
(285 vs 40,000 GPT-2 tokens), and a causal line is among those 15 in 94% of incidents.

But the incidents are generated by a simulator I wrote, and the model was trained on incidents from
the same simulator with the same fault taxonomy. It shows the pipeline works end to end. It does not
show the model would find a real production root cause. I'd rather say that in paragraph six than
have someone find it in the fine print.

## Log data is >90% duplicates, which changes everything

HDFS is 11 million lines. After masking, it is **57 distinct lines**. BGL is 4.7 million lines and 1,181
distinct masked lines. That has three consequences:

1. The encoder only ever needs to embed each distinct line once. The runtime's "template cache" is not
   an optimisation on top of the model, it *is* the reason the model is cheap.
2. "0.5-1B tokens of pretraining" (my plan's number) is meaningless when the whole corpus is ~59k
   distinct lines / 2M tokens. I trained 12k steps on distinct lines and watched validation loss flatten.
3. Splits leak in a very specific way. Only 38% of BGL test lines have a masked text seen in train, but
   97-100% for HDFS, Linux, Apache, OpenStack... in-distribution F1 on those systems is mostly template
   lookup. I report the leakage table next to the F1 table.

## A masking bug I only found by counting

After the first full pipeline run everything looked fine — and the pretrained encoder was no better than
a random one. I looked for why. 65,536 of BGL's "distinct" masked lines were the same message,
`generating core.<N>`: my number rule refused to mask digits preceded by a dot. That was 36% of all BGL
lines. Collapsing digits and counting variants per skeleton found it in seconds; I fixed the rule,
added identifier-suffix masking (`bglio12`, `step_7`), and re-ran the data, tokenizer and pretraining from scratch.
Lesson: count distinct-per-skeleton *before* you train anything.

## What worked

- **Supervised window model on in-distribution logs.** BGL F1 0.954 (time split) vs 0.545 for a supervised
  logistic regression on template counts and 0.335 for Drain3+DeepLog. HDFS F1 0.965 — but a template-count
  logistic regression gets 0.969, so HDFS is saturated and I don't count it as a win.
- **Few-label transfer.** On Thunderbird — a system excluded from every stage of training — fine-tuning on
  just 1% of its labels (2,100 windows) gives F1 0.985, above a logistic regression trained on **all** its labels (0.858).
- **Quantization.** Dynamic int8 costs <= 0.5 F1 points and shrinks the model from 148 MB to 37.5 MB.

## What didn't work (the interesting part)

- **Zero-shot transfer.** The supervised model and the unsupervised template-NLL model both score at or
  below the always-predict-anomaly baseline on the unseen system, and continuing the unsupervised objective on the
  target's unlabelled logs didn't rescue it. Alert taxonomies differ per system and I did not build anything that bridges them.
- **Pretraining did not measurably help in-distribution.** A random-init encoder matches the pretrained one
  (BGL F1 0.939 vs 0.948, RCA Recall@5 0.917 vs 0.917): with ~1k templates per system, a random projection is
  already injective. The plan's embedding gates (nearest neighbour shares the Drain3 template >= 90%; linear
  probe beats TF-IDF) were **not** met (68% and no).
- **SimCSE made embeddings worse** (44% vs 68% nearest-neighbour agreement): with distinct lines as
  instances, in-batch negatives push apart lines of the same template.
- **The tokenizer did not hit its 2x goal.** 1.5x fewer tokens than raw GPT-2 on average, 1.3x on the
  unseen system. Masking shortens ID-heavy lines (HDFS 2.5x, OpenStack 3.9x) and is a wash on short ones.
- **Killed containers are unrankable by design.** The two missed incidents were `container_kill`: the
  service logs nothing while down, and my labelling rule only counts lines from the target service.
  The real evidence — `connection refused` in the callers — isn't labelled causal, so the model was never rewarded for it.

## Cost and speed

Everything runs locally; there is no API spend to report, and I did not run a frontier-LLM baseline (no key available),
so I make no cost-per-million-lines claim against one. A 1.5B open model given a 1,500-token prompt sees ~2.5% of an
incident and scores Recall@5 = 0 — a weak baseline by construction, included only to show the input-size problem.
CPU serving numbers are in `docs/serving_benchmark.md`; the honest version pins the whole process tree to 4 cores.

## What I'd do next

1. Run the lab in Docker (the compose files exist, untested) and re-measure on real container faults.
2. Credit dependents' error lines as evidence for the failing service (service-level attribution metric).
3. Build a cross-system alert taxonomy so zero-shot has a chance, instead of hoping the encoder finds one.
4. Replace the Python parse+mask hot path with Rust; it is now the throughput bottleneck.
