# LogLens — Build Plan

Sep 30, 2026 · @Naman Kundra

## Overview

LogLens is a small log-intelligence model, trained from scratch, that flags incidents and ranks the log lines that explain them, running on a laptop CPU with zero LLM API calls.

**The problem.** On-call engineers and AI SRE agents drown in logs. Pushing millions of lines into a frontier LLM is slow, expensive, and often blocked by privacy rules. Classic tools (template parsers + LSTMs) detect anomalies but cannot say which lines matter.

**The pitch.** "I built the perception layer that makes on-call agents affordable: a 30M-parameter model that reads raw logs on CPU and hands the agent the 15 lines that matter out of 80,000."

**Who it is for.** AI/infra/observability startups, AI SRE companies, and any team hiring for ML engineering or backend + ML roles. It also becomes the specialist model inside the AI on-call investigator project.

**What makes it yours.** A log-aware tokenizer, a two-level encoder, a fault-injection lab that produces root-cause labels, int8 CPU serving, and an honest benchmark against frontier LLMs.

## Goals and success criteria

The project succeeds if LogLens gets within about 10% of a frontier LLM on root-cause ranking while running on CPU at under 1/100th of the cost. Targets below are starting points; tighten them after the first baseline run.

| Goal | Metric | Target |
| --- | --- | --- |
| Find the cause | RCA Recall@5 on fault-injection incidents | ≥ 0.80, and ≥ 90% of the frontier LLM's score |
| Detect incidents | Anomaly F1 on BGL / Thunderbird (time-based split) | Within 3 points of the best published baseline you reproduce |
| Generalize | F1 on a held-out, unseen log system (zero or few labels) | Beats Drain + DeepLog trained on that system |
| Run cheap | Throughput on a 4-core laptop CPU, int8 | ≥ 20,000 lines/s with template cache |
| Stay accurate after quantization | F1 drop FP32 → int8 | ≤ 2 points |
| Stay small | Total parameters / model file size | ≤ 50M params / ≤ 60 MB int8 |
| Show the economics | Cost per 1M lines vs frontier LLM API | Reported with the price and date used |

If LogLens loses on any metric, the result still gets reported. An honest table is the point.

## Scope

Version 1 is a model plus a thin serving layer, not an observability product.

**In scope**

- Plain-text and JSON application/system logs
- Log-aware tokenizer (masking + BPE)
- Two-level model: line encoder + window model with anomaly and suspicion heads
- Unsupervised (no-label) and supervised anomaly modes
- Fault-injection lab on a microservice demo app, with root-cause labels
- Baselines: Drain + DeepLog, LogBERT-style, small open LLM, frontier LLM API (evaluation only)
- int8 ONNX CPU inference, template cache, CLI, HTTP API, Docker image
- Tool integration with the on-call agent

**Out of scope (v1)**

- Metrics and traces (logs only)
- Natural-language explanations generated by LogLens itself
- Multi-tenant hosting, auth, dashboards, alert routing
- GPU inference and models above 100M parameters
- Real production customer data

## Phases

Nine phases, each with a hard exit gate. Do not start a phase until the previous gate passes; the Implementation Plan has the step-by-step work for each.

### Phase 0 — Setup (2–3 days)

- **Goal:** a clean repo, environment, and experiment tracking.
- **Deliverables:** repo skeleton, pinned environment, CI running lint + unit tests, W&B (or MLflow) project.
- **Exit gate:** `make test` passes in CI; a dummy training run logs to the tracker.

### Phase 1 — Data pipeline (week 1)

- **Goal:** every Loghub system normalized into one schema with time-based splits.
- **Deliverables:** download scripts, per-system parsers, Parquet shards, split manifest, data stats report.
- **Exit gate:** HDFS, BGL, Thunderbird (subset) and 5+ unlabeled systems in Parquet; no timestamp overlap between train and test.

### Phase 2 — Fault-injection lab (weeks 1–2, in parallel)

- **Goal:** logs with ground-truth root causes.
- **Deliverables:** Docker Compose lab, load generator, fault injector with 8+ fault types, incident label files.
- **Exit gate:** ≥ 150 labeled incidents across ≥ 8 fault types, each with the causal service and the causal log lines marked.

### Phase 3 — Tokenizer (week 2)

- **Goal:** a log-aware tokenizer that beats GPT-2's on efficiency.
- **Deliverables:** masking rules, trained BPE (8k–16k vocab), tokenizer tests, comparison report.
- **Exit gate:** ≥ 2× fewer tokens per line than GPT-2 on held-out systems; masking unit tests pass.

### Phase 4 — Line encoder pretraining (weeks 3–4)

- **Goal:** a pretrained encoder that produces useful line embeddings.
- **Deliverables:** model code, pretraining run, checkpoint, embedding sanity report.
- **Exit gate:** masked-token loss plateaus; nearest neighbours of a line share its template in ≥ 90% of spot checks.

### Phase 5 — Window model and heads (week 5)

- **Goal:** anomaly score and per-line suspicion score.
- **Deliverables:** window model, unsupervised and supervised training scripts, fine-tuned checkpoints.
- **Exit gate:** beats Drain + DeepLog on BGL F1; RCA Recall@5 ≥ 0.6 on the lab validation set.

### Phase 6 — Baselines and evaluation (week 6)

- **Goal:** the benchmark table.
- **Deliverables:** baseline runs, LLM evaluation harness, results table, error analysis notes.
- **Exit gate:** every cell of the benchmark table filled from a reproducible script with a fixed seed.

### Phase 7 — CPU serving (week 7)

- **Goal:** fast int8 inference and a usable interface.
- **Deliverables:** ONNX export, int8 model, template cache, CLI, HTTP API, Docker image, CPU benchmark.
- **Exit gate:** throughput and int8 accuracy targets from Goals met on a 4-core laptop.

### Phase 8 — Integration and release (weeks 8–9)

- **Goal:** LogLens inside the on-call agent, published and explained.
- **Deliverables:** agent tool, live demo, Hugging Face model + card, README, blog post, 2-minute video.
- **Exit gate:** a stranger can clone the repo, run the demo in under 15 minutes, and reproduce the headline number.

## Resources and budget

The whole project fits in roughly ₹3,000–8,000 of spend, mostly GPU rental and LLM API calls for evaluation. All figures are approximate; check current prices before you commit.

| Item | What | Approx. cost |
| --- | --- | --- |
| Local machine | Laptop with 16 GB RAM, Docker; used for data, lab, CPU serving | Already owned |
| GPU for pretraining | One RTX 4090 or A100 on Vast.ai / RunPod, \~15–30 GPU-hours total | ₹1,500–4,000 |
| Free GPU fallback | Kaggle (weekly quota) or Colab for fine-tuning and ablations | Free |
| Frontier LLM API | Evaluation only, on a sampled test set (not all logs) | ₹1,000–3,000 |
| Storage | Loghub raw + Parquet, checkpoints | \~50–100 GB disk |
| Tracking | Weights & Biases free tier or self-hosted MLflow | Free |
| Hosting | Hugging Face Hub for weights, GitHub for code | Free |

**Datasets:** Loghub / Loghub-2.0 (HDFS, BGL, Thunderbird, OpenStack, Hadoop, Spark, Zookeeper, Linux, Apache, and others), plus your own lab logs.

**Core tools:** Python 3.11, PyTorch, Hugging Face `tokenizers`, Polars/PyArrow, ONNX Runtime, FastAPI, Typer, Docker Compose, Locust, `tc`/Pumba for fault injection, pytest.

**Open question:** start date. Lockstep is already planned for about 6 weeks, so decide whether LogLens runs after it or in parallel at half pace (which roughly doubles this timeline).

## Risks and mitigations

The biggest risk is the fault-injection lab eating weeks; timebox it and cut fault types before cutting incident count.

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Fault-injection lab is flaky or slow to build | Blocks RCA labels, the headline result | Timebox to 8 days; start with 4 fault types; script everything; fall back to a public RCA benchmark if needed |
| Data leakage from random splits | Inflated, non-credible results | Time-based splits only; dedupe test lines against train templates; document it |
| HDFS/BGL already near-saturated | Anomaly numbers look unimpressive | Lead with RCA ranking and unseen-system transfer, not HDFS F1 |
| Masking removes signal (e.g. error codes, durations) | Lower accuracy | Keep bucketed values (`<DURATION:10s+>`), keep status codes; ablate masking levels |
| Pretraining underperforms or diverges | Weak embeddings, lost GPU money | Smoke-test on 1% data locally first; warmup + grad clipping; checkpoint every 30 min |
| Class imbalance in labels | Model predicts "normal" always | Report PR-AUC; weighted loss; threshold tuned on validation only |
| Frontier LLM eval gets expensive | Budget overrun | Evaluate on a fixed 300–500 window sample; cache responses |
| Scope creep (dashboards, traces, UI) | Project never ships | Out-of-scope list is binding for v1 |
| Parallel work (Lockstep, placements) | Timeline slips | Weekly checkpoint; each phase ships something usable on its own |
